# Issue #11: acceptance на растущем префиксе

Целевая модель: `Qwen/Qwen3.6-35B-A3B`, BF16, TP=1, одна GPU,
`config.json` задаёт один активный запрос, `config-b8.json` — до восьми
(`max_num_seqs` в конфигурации). Для полного прогона выбран режим до восьми.
Runner поддерживает несколько одновременных запросов на той же GPU,
с отдельным учётом каждого запроса и суммарной скоростью батча в `batches.jsonl`.
Разные значения concurrency не объединяются на одном графике.
Нативный контекст — **262 144**, лимит эксперимента —
**393 216 токенов**, включая вход. RoPE остаётся исходным, **YaRN выключен**.
Источник: [карточка Qwen](https://huggingface.co/Qwen/Qwen3.6-35B-A3B).

## Протокол

- 50 примеров каждого домена: MATH-500, HumanEval, синтетические разговоры UltraChat `test_sft`,
  десять неарифметических задач BBH (по 5 примеров).
- В чате сохраняется история до второго пользовательского сообщения; простым
  фильтром исключаются явные запросы про код и математику. Это эвристическое
  разделение доменов, а не гарантия полного отсутствия пересечений.
- Исходные короткие промпты продолжаются непрерывно до общего лимита контекста.
  Входы не дополняются повторением текста. Поэтому измеряется рост контекста
  через генерацию, а не эффект длинного входного документа.
- `ignore_eos=True`, greedy decoding, thinking включён. Все методы получают
  одинаковые сохранённые token IDs. Продолжения после первого EOS учитываются
  отдельно; они не интерпретируются как качество естественных ответов.
- Начальные промпты одинаковы, но дальнейшие greedy-траектории не считаются
  побитово одинаковыми: в короткой проверке AR и MTP уже наблюдались расхождения.
  Это сравнение свободной генерации по длине префикса; сравнение на идентичном
  тексте продолжения потребовало бы отдельного эксперимента с фиксированной траекторией.
- Без спекуляции, встроенный MTP, Z-Lab DFlash, EAGLE 3.1 SpecDrift.
  Два бюджета: 3 и 7 предложенных токенов. Для DFlash это блоки 4 и 8 с бонусным
  токеном. Версии всех весов закреплены в `config.json`.
- Оба драфтера также разрешено запускать до 393 216, чтобы vLLM не выключил
  спекуляцию на границе их конфигураций. Через callable `hf_overrides` увеличивается
  `max_position_embeddings` у target и драфтеров: это расширяет таблицу обычного
  RoPE, сохраняя `rope_theta`, `rope_type=default` и исходные частоты.
  Без этого у драфтера возможен выход за выделенную таблицу, даже если scheduler
  разрешает длинную последовательность. YaRN не включается; нативная граница
  по исходному чекпойнту остаётся 262 144.
- У EAGLE-чекпойнта включены `fc_norm` и `norm_output`; это EAGLE 3.1,
  его нельзя подписывать как исходный EAGLE-3. У выбранной версии нет model card:
  точная обучающая смесь и длина обучения не установлены.
  В опубликованных весах нормализации названы `fcs.{0,1,2}.weight`,
  а vLLM 0.32 ожидает `fc_norm.{0,1,2}.weight`. `checkpoints.py` создаёт
  отдельную локальную копию с переименованными ключами и проверяет побитовое
  равенство всех тензоров после сохранения. Исходные веса не изменяются;
  SHA-256 обеих файлов и отображение ключей записываются в `metadata.json`.
- Выбранный DFlash — опубликованная версия с обучением на 40K и sliding-window
  attention. Результаты относятся к этому чекпойнту, а не к любой версии DFlash.
- Synchronous scheduling и одинаковое логирование во всех режимах.
  Prefix caching выключен. Это контролируемый эксперимент, не максимум throughput сервера.
- Включён `VLLM_COMPUTE_NANS_IN_LOGITS`; счётчики NaN сохраняются в сырые логи,
  чтобы отделять отказ драфтера от численной деградации target за нативной границей.

## Запуск

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r benchmarks/long_context/requirements.txt
.venv/bin/python -m benchmarks.long_context.download
.venv/bin/python -m benchmarks.long_context.prepare
.venv/bin/python -m pytest benchmarks/long_context/test_plot.py -q

# UUID нужно выбрать по nvidia-smi; sweep проверяет свободную память перед запуском.
mkdir -p runs
nohup .venv/bin/python -m benchmarks.long_context.sweep \
  --gpu GPU-UUID --config benchmarks/long_context/config-b8.json \
  --output runs/issue11-20261024-b8 \
  > runs/issue11-controller.log 2>&1 &
```

Сначала все семь конфигураций проходят короткую проверку на четырёх доменах,
затем каждый метод проходит техническую проверку диапазона позиций (`boundary/`):
искусственно склеенный и повторённый префикс длиной 393 088 плюс 128 новых токенов.
Она проверяет реальные CUDA/RoPE-операции у верхней границы и не входит в графики
или 200 исследовательских примеров. После неё выполняется
длинная проверка на первых восьми промптах (`pilot/`), затем оставшиеся
192 промпта (`full/`). Pilot входит в общие 200 примеров и не дублируется.
При concurrency=1 размеры этих частей составляют 4 и 196.
Ошибка останавливает очередь и записывается
в `status.json`; повреждённый результат не считается успешным. Полные логи
хранятся локально в `runs/`, в Git не добавляются. При перезапуске завершённые
конфигурации пропускаются, незавершённые требуют разбора перед повтором.

## Логи и графики

- `metadata.json`: веса, параметры, версии библиотек, GPU, хеш данных, статус.
- `progress.json`: обновляемые каждые десять секунд длины запросов,
  счётчики принятия, NaN и вытеснений запросов из KV-кеша.
- `effective_vllm_config.txt`, `console.log`: фактическая конфигурация и вывод движка.
- `rounds.jsonl.gz`: длина префикса до каждого раунда, предложенные/принятые
  драфт-токены, выходные token IDs, время шага и фаза относительно первого EOS.
  `proposed` и `accepted` — счётчики vLLM. V2 Model Runner передаёт scheduler
  маркеры `-1` вместо фактических ID предложенных токенов: они сохраняются
  в `scheduled_draft_token_ids`, а `draft_token_ids` в этом случае равен `null`
  и `draft_token_ids_available=false`. В ранних smoke/boundary-логах эти
  маркеры лежат непосредственно в `draft_token_ids`; это не настоящие token IDs.
  Все фактически выданные target токены доступны в `token_ids` и выходных потоках.
- `requests.started.jsonl`, `requests.jsonl`: соответствие внутренних ID,
  завершённость, фактическая длина, TTFT, полное время, tok/s, хеш ответа.
- `*.tokens.jsonl.gz`, `*.text.txt.gz`: все выходные токены и декодированный текст.
- `plots/`: PNG/PDF и CSV с acceptance, средней длиной принятого драфта
  и скоростью по длине префикса, а также парным ускорением относительно AR.
  Отдельные графики для всей генерации,
  части до первого EOS и после него. Пунктир — нативная граница 262 144.

Acceptance определяется как `accepted / proposed`, бонусный токен target
не входит в числитель. Среднее число принятых токенов за раунд тоже не включает
бонус. Сначала считаются метрики по каждому промпту в бинах 8192 токена, затем
промпты усредняются с равным весом; 95% интервалы — bootstrap по промптам.
Число наблюдаемых промптов в каждом бине сохраняется в `curves.csv`.
Скорость по бинам относится к одному запросу и использует время шагов scheduler
без prefill; суммарная скорость одновременно обрабатываемого батча записана
отдельно в `batches.jsonl`. Скорость целого
запроса включает prefill и клиентское обслуживание. Они подписываются отдельно.

```bash
.venv/bin/python -m benchmarks.long_context.plot \
  runs/issue11-20261024-b8/pilot/*-k* \
  runs/issue11-20261024-b8/full/*-k* \
  --output runs/issue11-20261024-b8/plots --include-partial
```

Промежуточные графики обновляются каждые десять минут и после каждой завершённой
конфигурации. Неполный прогон явно помечается. Пустые участки не экстраполируются.
